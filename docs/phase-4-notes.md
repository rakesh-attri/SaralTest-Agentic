## How it works (short)

1. **The model never writes code.**
   - For each APPROVED case, the coder role fills a test IR: actions and assertions over page-object members,
     recipe data and value refs.
   - `irProblems` rejects any IR where:
     - a case step is not implemented;
     - an assertable expectation is not asserted, or an assertion cites evidence its case step does not cite;
     - a literal is not found in the case text, the recipe or the UI labels;
     - a length is not stated in the case step;
     - an API error code does not follow from metadata;
     - an element is used on a page that is not open at that point of the flow;
     - a UI-created record is adopted under a value the test did not type;
     - a keyboard check does not cover all fields.
   - Code renders the spec from the IR (`render.ts`). A model that never produces a valid IR yields a
     `test.fixme` skeleton, labelled mechanical and REVIEW_REQUIRED.
2. **Locators come only from the registry.** Page objects are generated by code. "Resolve" means:
   - tsc and ESLint pass;
   - `playwright test --list` loads and lists every spec, without executing it;
   - every member a spec uses resolves in its page state as the persona: exactly one match, visible, enabled.
3. **Pass 2** reruns the IR checks and adds AST checks (no `expect` under a condition, no sleeps, no raw
   fetch/locators, no `.only`), meta/tag checks and the tool results. A judge on a different model family checks
   "test matches the case, assertions not weakened". Regenerable findings go back to the generator once. The QA
   Lead then settles: H findings of blocking rules → BLOCKED, any other escalation → REVIEW_REQUIRED.
4. **Data** follows `docs/test-data-recipe-guide.md`: every write is guarded and audited write-ahead, every state
   change is in the ledger, cleanup touches only records that still carry this run's tag, and an independent
   re-query proves that nothing is left.
5. **a11y rule (operator):** the axe scan is limited to the dialog. Salesforce-owned violations are recorded as a
   known baseline. Only violations in custom namespaces fail the test, together with the keyboard check
   (reachability, focus trap, visual reading order). The judge prompt carries the rule as an accepted decision.

## Coder diagnostics and fix (2026-11-21, after the PR was opened)

In `run-p4-live-1` every accepted test IR came from the Gemini **fallback**, and my console filter had dropped the
reasons. The run log now keeps them: `runs/<id>/logs/run.log` holds every warning and error with the error message,
and every build writes `model-attempts.json` plus a "Model attempts" table. Each coder was run alone with
`qa build --coder <model>` (no fallback) and probed with `scripts/probe-coder.ts`, which uses the real generator prompt.

### Why each coder failed

| Model | Model id / context | JSON / tools | Real prompt | Failure |
|---|---|---|---|---|
| NIM `poolside/laguna-xs-2.1` | listed; context not reported | plain, `json_object`, strict `json_schema` and tools all work | 9,633 tokens, ~12 s | No transport errors. The replies broke the IR contract: page refs used as record refs, camelCase labels, invented kinds and elements. Text mode never produced a valid IR (`run-p4-coder-nim-1`: 0/7). |
| Groq `openai/gpt-oss-120b` | listed; 131,072 | `json_object` / `json_schema` → HTTP 400 `json_validate_failed`; tools OK | 9,630 tokens | HTTP 413: on_demand limit **8,000 TPM**. Our config said 6,000, so our limiter refused every call as TRANSIENT, the build node retried and wrote no report (`run-p4-coder-groq-1`). |
| Groq `qwen/qwen3.8-27b` | listed; 131,072 | all work | 9,550 tokens | HTTP 413: **7,000 input** and **1,000 output** tokens/minute; one answer is ~1,700 tokens. |

### Fix

- **Prompt 9.6k → ~3.1k tokens.**
  - A compact typed IR contract replaces the 18.9k-char JSON Schema; a test keeps it in sync with the schema.
  - Each case gets only the catalog members and field facts it can use.
- **`responseFormat: json_object`** for the NIM coder (`config/models.yaml`). Groq's quota is set to the measured 8,000.
- **Meaning-preserving normalization** before the checks:
  - page-style record refs → recipe step ids;
  - kebab-case labels;
  - value shorthand without `kind`;
  - omitted evidence → the case step's own evidence;
  - the cleanup `adopt` of a UI-created record, when unambiguous (added by code, noted in the spec).
- **Stricter oracle checks:**
  - "not saved" must use a run-unique value the test typed;
  - a typed value is read from the record the test created;
  - every record created in the UI is adopted.
- **Other fixes:**
  - an oversize request is TOOL_UNAVAILABLE (it never fits), not TRANSIENT;
  - `expect` is imported only when used;
  - reflection messages carry concrete repairs.

## Judge resilience and code-owned cleanup (2026-11-25, operator request)

- **`qa build` survives a judge outage.**
  - The review2 node retries a TRANSIENT judge failure with the policy backoff (2 / 8 / 30 s). The router chain is
    the provider fallback: NIM judge → Gemini.
  - If both still fail, the round is deterministic-only and nothing becomes APPROVED ("judge unavailable"). A
    DEGRADED issue is recorded, and **the manifest is always written.**
  - Proof: `build.test.ts` (judge always 503), and live run run-p4-build-decided-4 (round 1 judge 503 ×4, round 2
    judge answered).
- **Record cleanup is no longer written by the model.**

    has one is BLOCKED by pass 2.

  - The data engine first proves the record is ours (`CreatedById` = the persona's user, `CreatedDate` ≥ test start
    − 5 min), then tags it and adds it to the cleanup ledger.

    assertion.
